# План реализации Brief OS

> План составлен до начала разработки. После каждого этапа работа останавливается: создаётся отчёт в `agent-conversation-history.md`, затем ожидается согласование Юрия на переход дальше.

## Этап 0. Документация и проектные правила

**Результат:** папка проекта, подробное ТЗ, план, скопированные гайды, история.

- Создать структуру `/root/brief`.
- Скопировать `guides/` из `AI-design-systems`.
- Создать подробное ТЗ.
- Создать дневник проекта.
- Зафиксировать предложения и открытые вопросы отдельно.
- Проверить кодировку файлов: UTF-8 с BOM для русскоязычных документов.

**Приёмка:** документы доступны в проекте, гайды лежат в `/root/brief/guides`, разработка не начата без подтверждения.

## Этап 1. Архитектурный каркас и визуальная оболочка

**Результат:** запускаемый Nuxt-проект без бизнес-логики, с авторизационным экраном-заглушкой и AppShell.

- Создать `package.json`, `nuxt.config.ts`, базовую структуру Nuxt 4.
- Подключить SCSS через `@use`.
- Создать дизайн-токены для светлой и тёмной тем.
- Реализовать `AppShell`, `Sidebar`, `Topbar`, `ProjectSwitcher`, `ThemeToggle`, `UserMenu`.
- Реализовать адаптивную mobile-first раскладку.
- Проверить соответствие интерфейсу Impression.

**Приёмка:** приложение запускается локально, shell отображает только элементы из ТЗ, темы переключаются, мобильная раскладка работает.

## Этап 2. База данных и авторизация

**Результат:** реальный вход, выход, сессии и bootstrap admin.

- Подключить PostgreSQL.
- Создать Drizzle schema.
- Добавить пользователей, роли и permissions.
- Реализовать хэширование паролей.
- Реализовать cookie-based sessions.
- Добавить seed временного `admin/admin`.
- Добавить смену пароля администратора.
- Ограничить API и страницы middleware-проверками.

**Приёмка:** admin входит, выходит, меняет пароль; защищённые страницы недоступны без сессии.

## Этап 3. Пользователи, роли, проекты и права

**Результат:** администратор управляет пользователями, проектами, участниками и правами.

- CRUD пользователей.
- CRUD проектов.
- Назначение ролей и участников проекта.
- Таблица прав в разделе «Настройки».
- Отдельное право `stage.move_backward`.
- Ограничение данных по проекту и роли.

**Приёмка:** разные пользователи видят только разрешённые проекты и действия; клиентский доступ не расширяется за пределы бриф-ссылок.

## Этап 4. Этапы, чеклисты и переходы

**Результат:** рабочие этапы и контроль готовности.

- Создать этапы Согласование, Дизайн, Разработка, Деплой, Поддержка.
- CRUD нескольких чеклистов на этапе.
- CRUD пунктов.
- Статусы `pending`, `completed`, `skipped`.
- Признак обязательности.
- Прогресс и блокировка перехода.
- Закрытие этапа с подтверждением.
- Возврат на предыдущий этап с причиной и проверкой права.
- История переходов.

**Приёмка:** переход вперёд невозможен при незакрытом обязательном пункте; возврат доступен только разрешённым пользователям.

## Этап 5. Конструктор и workflow брифов

**Результат:** единый бриф без рабочих копий с цепочкой дизайнер → менеджер → клиент → менеджер → дизайнер.

- CRUD брифов.
- Вопросы и типы полей.
- Сортировка и обязательность вопросов.
- Статусы брифа.
- Редактирование менеджером до отправки клиенту.
- Принятие менеджером.
- Возврат брифа менеджеру, дизайнеру или другому разрешённому адресату с комментарием.
- Ограничение редактирования: изменять бриф может только текущий адресат.
- История изменений и аудит доступны сотрудникам, клиенту история не показывается.
- Журнал брифов в проекте с фильтрацией по этапу, статусу, участникам и датам.
- Просмотр текущей и каждой сохранённой версии брифа на любом этапе жизненного цикла.
- Read-only просмотр исторических снимков без изменения текущей версии.
- Запись всех действий с брифом в историю проекта.

**Приёмка:** бриф проходит согласованный маршрут, данные не теряются, копии рабочего брифа не создаются, а текущая и исторические версии доступны в журнале проекта.

## Этап 6. Безопасные ссылки клиента и заполнение

**Результат:** публичная форма `/brief/<token>`.

- Генерация криптографического токена.
- Хранение только хэша токена.
- Режимы fill/edit/view.
- Заполнение всех типов полей.
- Загрузка файлов.
- Отправка формы.
- Перевод старой ссылки в read-only.
- Новая ссылка с предыдущими ответами.
- Read-only просмотр старых ссылок.
- Срок действия публичной ссылки 30 дней без удаления данных.
- Проверка срока действия и статуса ссылки.
- Мягкое удаление брифа с сохранением истории.
- Запись изменённых полей, старых и новых значений.
- Просмотр брифа и его версий из истории проекта для сотрудников.

**Приёмка:** клиент видит только конкретный бриф; старый токен не редактирует данные; новый токен открывает прежние ответы для правки.

## Этап 7. Комментарии, заметки и уведомления

**Результат:** обсуждение на уровне проекта и этапа.

- Внутренние заметки.
- Комментарии с visibility.
- Собственные CRUD-действия.
- Уведомления внутри приложения.
- Уведомления о действиях с брифом и этапом.

**Приёмка:** внутренние комментарии недоступны клиенту; участники получают уведомления согласно правам.

## Этап 8. Проверка, документация и production

**Результат:** опубликованный MVP.

- Unit/integration проверки API.
- E2E проверки входа, ролей, чеклистов, переходов и ссылок.
- Проверка accessibility и responsive.
- Production build.
- PM2 ecosystem.
- Caddy для `brief.yuriybevov.ru`.
- Миграции и seed на сервере.
- Проверка HTTPS и основных сценариев.
- Финальный аудит по ТЗ.

**Приёмка:** production работает, основные роли и сценарии проверены, отчёт сохранён в истории.

## Правило перехода между этапами

После завершения каждого этапа я:

1. запускаю предусмотренные проверки;
2. фиксирую изменённые файлы;
3. добавляю отчёт в `agent-conversation-history.md`;
4. сообщаю результат в чате;
5. жду согласование Юрия;
6. только после согласования начинаю следующий этап.
