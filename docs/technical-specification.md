# Подробное техническое задание

## Проект

**Рабочее название:** Brief OS  
**Домен:** `https://brief.yuriybevov.ru`  
**Назначение:** многопользовательское веб-приложение для структурирования разработки веб-проектов, сбора данных по этапам, работы с чеклистами и брифами.

## 1. Цели системы

1.1. Собирать и хранить данные, необходимые на разных этапах разработки сайта или приложения.

1.2. Организовать чеклисты по этапам и не допускать перехода дальше без выполнения обязательных пунктов.

1.3. Организовать передачу брифов между сотрудниками агентства и клиентами без потери ответов и истории изменений.

1.4. Разделить внутренние данные агентства и данные, доступные клиенту.

1.5. Дать руководителям возможность управлять правами пользователей и историей переходов проекта.

## 2. Зафиксированные решения

2.1. Стек реализации: Nuxt 4, PostgreSQL, Drizzle ORM, cookie-based sessions, SCSS и БЭМ.

2.2. Визуальное направление: интерфейс `impression.yuriybevov.ru` — тёмная рабочая оболочка, фиксированный сайдбар, синий акцент, компактная навигация, светлая и тёмная темы.

2.3. Этапы верхнего меню: Согласование, Дизайн, Разработка, Деплой, Поддержка.

2.4. Клиент не получает полноценный доступ к приложению. Его единственная задача — заполнение брифов, открытых по ссылкам. Дополнительный функционал для клиента отсутствует.

2.5. Права пользователей назначаются в разделе «Настройки». Отдельное право: «Возвращать проект на предыдущий этап».

2.6. Бриф не копируется при передаче от дизайнера менеджеру и от менеджера клиенту. Используется один объект брифа с историей изменений.

2.7. Дизайнер может отправить менеджеру бриф, который предназначен клиенту. Менеджер может отредактировать его перед отправкой клиенту.

2.8. Заполненный клиентом бриф возвращается менеджеру. Менеджер может принять его или вернуть далее дизайнеру на доработку.

2.9. Клиент получает доступ только по ссылке формата:

```text
https://brief.yuriybevov.ru/brief/<token>
```

2.10. После отправки заполненного брифа текущая ссылка становится доступной только для просмотра. Для повторного редактирования создаётся новая ссылка на тот же бриф с ранее заполненными данными.

2.11. История изменений хранится для аудита, но рабочая сущность брифа остаётся единой.

2.12. Бриф по своей сути — это список вопросов с ответами конкретного пользователя системы или клиента.

2.13. Создание брифа, изменение его статуса, редактирование вопросов и ответов, отправка, возврат, принятие, создание ссылок и другие действия с брифом обязательно записываются в историю проекта.

2.14. Каждый бриф должен быть доступен для просмотра в истории проекта на любом этапе его жизненного цикла: в черновике, после отправки, во время заполнения, после возврата, после принятия и после закрытия.

2.15. Просмотр брифа из истории проекта открывает соответствующую историческую версию и не изменяет текущую версию брифа.

## 4. Авторизация

4.1. Вход выполняется по логину и паролю.

4.2. Для первичного запуска создаётся временный пользователь:

```text
login: admin
password: admin
role: administrator
```

4.3. Пароль хранится только в виде хэша.

4.4. После первого входа администратор должен иметь возможность сменить пароль.

4.5. Сессия хранится в защищённой cookie.

4.6. Неавторизованный пользователь перенаправляется на страницу входа.

4.7. Публичной регистрации пользователей нет. Пользователей создаёт администратор.

## 5. Общая структура интерфейса

### 5.1. Шапка

Слева:

- название текущего проекта;
- текущий этап;
- статус проекта.

Справа:

- текущее время;
- кнопка уведомлений при наличии функционала;
- кнопка «Выйти» для авторизованного пользователя;
- кнопка «Войти» для неавторизованного состояния.

### 5.2. Сайдбар

Верхняя часть:

- текстовый логотип «Логотип»;
- выбор проекта через выпадающий список.

Основное меню:

- Согласование;
- Дизайн;
- Разработка;
- Деплой;
- Поддержка.

Нижнее меню:

- Настройки;
- Создать бриф;
- Создать чеклист.

Футер сайдбара:

- переключатель светлой/тёмной темы;
- аватар;
- имя пользователя;
- роль пользователя.

### 5.3. Контентная область

Каждый рабочий экран состоит из:

1. заголовка раздела;
2. кнопок действий справа;
3. основной функциональной области;
4. панели комментариев справа.

На узких экранах панели располагаются вертикально.

### 5.4. Общий футер

Пока отображается текст:

```text
Сделано в
```

Логотип разработчика добавляется позднее.

### 5.5. Общие правила компонентов

5.5.1. Все кнопки удаления и деактивации во всём приложении, включая кнопки с текстом и иконочные кнопки, должны использовать danger-оформление на основе `--color-danger`.

5.5.2. Любое критичное действие, включая удаление, деактивацию, блокировку доступа, необратимое закрытие или другое действие с потенциальной потерей доступа/данных, всегда должно требовать подтверждения в модальном окне. Прямое выполнение таких действий по первому нажатию запрещено.

5.5.3. В приложении обязательно соблюдается компонентный подход и правило DRY. Если элементы интерфейса похожи визуально, выполняют одну роль и отличаются только содержимым, они реализуются одним общим компонентом с параметрами и слотами, без дублирования разметки, классов и логики.

5.5.4. При редактировании существующего элемента, паттерна, стиля или поведения обязательно проверяется весь проект на похожие или идентичные элементы. Если такие элементы есть, правка распространяется на весь однотипный паттерн, а похожие реализации объединяются в общий компонент или общий набор стилей, когда это оправдано.

5.5.5. Если список внутри разворачивающегося блока пуст, кнопка разворота остаётся в интерфейсе, но отображается неактивной. Это правило применяется к брифам, чеклистам и любым будущим однотипным блокам.

5.5.6. Нативные `select`, `checkbox`, `radio` и `input type="file"` не используются напрямую в рабочих шаблонах. Для этих элементов применяются базовые компоненты дизайн-системы.

5.5.7. Кнопки раскрытия и сворачивания аккордеонов, карточек, истории и других однотипных блоков реализуются через общий компонент `BaseDisclosureToggle`. Иконка раскрытия не используется отдельно без тега `button`.

## 9. Брифы

### 9.1. Смысл брифа и общая модель

9.1.1. Бриф — это список вопросов и ответов, заполненных конкретным пользователем системы или клиентом.

9.1.2. Бриф является частью истории проекта и не существует независимо от проекта и этапа, в контексте которого он был создан или использован.

9.1.3. Бриф может проходить через нескольких участников, но рабочая сущность брифа остаётся единой: копии для каждого участника не создаются.

9.1.4. Изменения вопросов, ответов, статуса, адресата, ссылок и маршрута сохраняются в истории версий и в журнале действий проекта.

9.1.5. Каждый сохранённый бриф и каждая его версия должны быть доступны для просмотра на любом этапе жизненного цикла.

9.1.6. Исторический просмотр является read-only и не меняет текущие ответы или статус.

9.1.7. Бриф может быть создан дизайнером для менеджера, хотя конечное назначение — клиент.

### 9.2. Жизненный цикл

```text
Черновик
→ Отправлен менеджеру
→ Редактируется менеджером
→ Отправлен клиенту
→ Заполняется клиентом
→ Заполнен клиентом
→ Возвращён менеджеру
→ Принят менеджером
→ Закрыт
```

Дополнительный маршрут:

```text
Заполнен клиентом
→ Возвращён менеджером дизайнеру
→ Доработан дизайнером/менеджером
→ Снова отправлен клиенту
```

9.3. Редактировать бриф может только пользователь, которому он в данный момент отправлен. Это правило распространяется на вопросы, типы полей, варианты ответов, обязательность и иные данные брифа.

9.4. После отправки брифа клиенту или другому адресату предыдущий пользователь получает режим только просмотра и больше не может менять структуру или ответы.

9.5. После отправки заполненного брифа текущая ссылка становится read-only.

9.6. Для повторного заполнения или доработки создаётся новая ссылка на тот же бриф. Старые ответы открываются в новой форме и могут быть изменены текущим адресатом.

9.7. Возврат брифа выполняется с указанием получателя и необязательного комментария. Получателем может быть менеджер, дизайнер или другой пользователь системы согласно текущему этапу и назначенным правам.

9.8. Каждый переход брифа между адресатами, включая возврат, отправку, принятие и повторную ссылку, записывается в историю проекта.

### 9.3. Поля брифа

Поддерживаются типы:

- text;
- textarea;
- radio;
- checkbox;
- select;
- multiselect;
- number;
- date;
- file.

Каждый вопрос содержит:

- текст вопроса;
- тип поля;
- обязательность;
- варианты ответа, если применимо;
- пояснение;
- порядок сортировки.

### 9.4. Ссылка брифа

Формат:

```text
https://brief.yuriybevov.ru/brief/<token>
```

9.4.1. Токен генерируется криптографически случайным способом.

9.4.2. В базе хранится хэш токена, а не открытый токен.

9.4.3. Ссылка имеет назначение: заполнение, повторное редактирование или просмотр.

9.4.4. По умолчанию публичная ссылка действует 30 дней с момента создания.

9.4.5. Истечение срока ссылки не удаляет бриф, ответы, версии или записи истории проекта.

9.4.6. Старая ссылка сохраняется после заполнения, но работает только в режиме просмотра до истечения срока доступа.

9.4.7. Истёкшая ссылка не позволяет редактировать форму и показывает сообщение о завершении доступа.

9.4.8. Новая ссылка открывает предыдущие заполненные данные для редактирования.

### 9.5. История брифов в проекте

9.5.1. В проекте должен быть отдельный журнал брифов с фильтрами по этапу, названию, статусу, отправителю, адресату и дате. Удалённые брифы скрыты из обычного списка, но доступны сотрудникам в истории с пометкой «Удалён».

9.5.2. В журнале отображаются все брифы проекта, включая архивные и завершённые.

9.5.3. Для каждого брифа доступны:

- текущий статус;
- текущий и предыдущие этапы;
- автор;
- участники цепочки передачи;
- дата создания и даты изменений;
- список версий;
- ссылки и их статусы;
- ответы на каждом зафиксированном шаге;
- история возвратов и принятия.

9.5.4. Просмотр конкретной версии должен показывать неизменяемый снимок вопросов, ответов, файлов, автора изменения, даты и причины изменения.

9.5.5. Переход проекта на другой этап не удаляет и не скрывает брифы предыдущих этапов.

9.5.6. Права просмотра истории проверяются по проекту и роли. Клиент не получает доступ к журналу проекта и историческим версиям через основной интерфейс.

### 9.6. Клиент

Клиент:

- не входит в основной интерфейс приложения;
- не видит сайдбар, проекты, настройки, чеклисты и внутренние комментарии;
- открывает только полученную ссылку;
- заполняет бриф;
- загружает файлы;
- отправляет бриф менеджеру;
- повторно редактирует бриф только по новой ссылке.

## 10. Комментарии

10.1. Комментарии привязаны к проекту и этапу.

10.2. Видимость комментария:

- internal — только сотрудники агентства;
- client_visible — доступен клиенту в предусмотренном контексте.

10.3. Клиент не получает общий интерфейс комментариев и не видит внутренние записи.

10.4. Комментарии поддерживают создание, редактирование собственного комментария и удаление собственного комментария с сохранением аудита.

- бриф отправлен;
- бриф заполнен;
- бриф возвращён менеджеру;
- бриф возвращён дизайнеру;
- бриф принят;
- проект переведён на другой этап;
- проект возвращён на предыдущий этап.

11.2. Email-уведомления не входят в первый этап реализации и могут быть добавлены позднее.

## 12. Файлы

12.2. Максимальный размер одного файла: 10 МБ.

12.3. Файлы хранятся на сервере, а в базе сохраняются метаданные.

12.4. Доступ к файлу проверяется сервером по правам пользователя и токену брифа.

## 15. Критерии готовности MVP

Перед завершением MVP необходимо проверить отдельный сквозной сценарий истории брифа: создание, отправка, редактирование текущим адресатом, заполнение, возврат, принятие, повторная ссылка и read-only просмотр всех сохранённых состояний сотрудником из истории проекта.

MVP считается готовым, если:

1. Администратор может войти и управлять пользователями.
2. Можно создать проект и назначить участников.
3. Можно выбрать проект и открыть этап.
4. Можно создать несколько чеклистов на этапе.
5. Переход блокируется незакрытыми обязательными пунктами.
6. Можно создать бриф с вопросами разных типов.
7. Менеджер может изменить бриф до передачи клиенту.
8. Клиент открывает только ссылку `/brief/<token>`.
9. Заполненный бриф возвращается менеджеру.
10. Менеджер может вернуть бриф дизайнеру.
11. Старая ссылка становится read-only.
12. Новая ссылка открывает предыдущие ответы для редактирования.
13. Работает история изменений.
14. Работают права пользователей, включая возврат этапа назад.
15. Работают светлая и тёмная темы.
16. Production доступен по `https://brief.yuriybevov.ru`.

## 16. История проекта и журнал брифов

16.1. История проекта — единый журнал действий и состояний проекта.

16.2. В историю проекта обязательно записываются все действия с брифами: создание, редактирование вопросов, изменение обязательности и типов полей, изменение ответов, отправка, получение, изменение статуса, возврат, принятие, создание и отзыв ссылок, загрузка и удаление файлов, а также удаление самого брифа.

16.2.1. Для изменений, где это применимо, в истории сохраняются изменённые поля, предыдущие значения и новые значения.

16.2.2. Удаление брифа выполняется мягко. Удалённый бриф скрывается из рабочего списка, но остаётся в истории проекта и доступен сотрудникам в режиме просмотра.

16.3. В истории хранится снимок брифа на момент значимого действия: список вопросов, ответы, адресат, автор действия, этап, статус, дата, комментарий и связанные файлы.

16.4. Сотрудник с правом просмотра проекта может открыть каждый бриф и любой сохранённый снимок на любом этапе жизненного цикла в режиме read-only.

16.5. История не удаляется при переходе проекта на следующий этап, возврате этапа или закрытии проекта.

16.6. Клиент не видит историю проекта и исторические версии брифа.

## 17. Ограничения первой версии

В первую версию не входят:

- полноценный клиентский кабинет;
- email-уведомления;
- интеграции с CRM;
- календарь;
- автоматический деплой проектов;
- сложный конструктор workflow;
- мобильное приложение;
- публичная регистрация.

## 18. Согласованные уточнения

18.1. Точные поля проекта и обязательность каждого поля — обязательность назначает создатель соответствующего брифа или чеклиста.

18.2. Разрешены безопасные форматы файлов. Точный whitelist и размер будут зафиксированы после проверки инфраструктуры, загрузчика и хранилища.

18.3. При возврате брифа указывается комментарий. Бриф может быть возвращён не только дизайнеру, но и пользователю другой роли, если это разрешено workflow и правами.

18.4. Редактировать бриф может только пользователь, которому он в данный момент отправлен. Менеджер не может менять структуру брифа после того, как бриф уже отправлен клиенту или другому текущему адресату.

18.5. История изменений и журнал брифов доступны только сотрудникам с соответствующим правом просмотра проекта. Клиент видит только текущую форму, ответы и разрешённые ему данные по ссылке.
